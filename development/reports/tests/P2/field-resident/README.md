# 河原野战移动数据常驻试玩版

双击[试玩常驻版野战.cmd](试玩常驻版野战.cmd)，在主菜单进入河原并点击「开始野战」。当前入口从本地提交 `256c03d` 建立独立游戏副本，导入资源并实际调用原生移动内核。环境为 Windows x64、Godot 4.7.2 Standard，游戏存档继续使用 `out/resident/play-bbcdc93/appdata`；窗口偏好与普通版共用。下文的性能数字来自原采样版本。[最新界面与窗口实测](../river-ui/README.md) · [镜头和快捷键](../field-controls/README.md) · [守阵自卫实测](../field-hud-contact/README.md)

## 版本与采样条件

P2-FIELD-INTEGRATION-034，试玩提交 `47ce2c3`。对照组使用上次已交付的 C++ DLL（SHA-256 前八位 `8da02c3c`）。新版按 MOV 已提交的兵员顺序复用位置、速度、朝向、移动目标和半径。新分片模式把步兵候选落点分给 Godot 线程池，涉及相邻士兵的裁决仍按原顺序执行。骑兵的转向按原公式计算。

同一台 Core Ultra 9 285K、RTX 3090，Forward+、960×600，地图种子 241124，500 名士兵、100 匹马，60 Hz 战斗、每显示帧最多补算两步。每种配置跑一场静止、一场有指令野战，分别从主菜单进入。站立和行军取第 121–440 步；行军场第 1 步后给四阵发移动令，第 900 步发自由攻击令，取首次命中至第 1260 步为接战窗口。初始化、加载和部署排除在这些统计之外。

试玩入口默认使用常驻串行预测。接战每步平均只需更新 33.7 行移动输入，准备时间从 2.647 降至 0.350 ms，连同有序避让与写回的推进阶段从 3.409 降至 1.034 ms。四分片的整场接战样本更快，但其原生调用均值从 0.124 增至 0.128 ms，站立与行军的调用均值也略升。单轮差异不足以把整帧收益归因于并行。

接战的完整移动和 AI 分别仍占 7.06 和 6.85 ms/步。平均一帧算两步，再加 18.26 ms 步外工作，整帧为 59.20 ms。CPU 侧的可视筛选、战斗数据读取、角色装配、快照应用和插值合计 9.29 ms/帧。这是后续可单独优化的显示开销。

## 行为、回滚与集成

- 交付版独立无头回放按步比对全部 1260 步的位姿、投射物与战斗事件摘要。首次命中在第 986 步，共 88 次发射、61 次有效命中，累计 2112 点伤害。在第 986 步注入失败后，画面和已提交世界仍停在第 985 步；重试复现相同命中。
- 独立 MOV 边界回归在 72 人起始名册、94 步中通过 8112 项检查，覆盖骑兵跨格、密集避让、跳跃落地、同槽换代、增援、地形重设和撤权重试。外部玩家回调中途改变控制权，以及失去控制的短队列重新并成长队列，均逐兵对照原脚本。另有开发自测 140 项通过。
- 最终无头回放使用串行预测。独立 1024 行输入在串行和四分片下返回相同字节，线程池计数证实分片确实执行。原生微基准另外使用真实行军的 16 份批输入，每种模式各执行 768 次完整调用，含提交与等待；串行/四分片平均为 106.17/104.49 µs，两者 P50 均为 103 µs。该结果只涵盖原生调用。[原生采样与源码](native-evidence.zip)
- 开发中的第一稿在真实桌面站立窗口有 0/320 步启用常驻路径，原因是每步的玩家零速度输入让全队回退。最终版让该玩家保留原序回调，其余 AI 继续复用数据。独审还发现事务外清地形后会读到过期路径，定向测试在第 92 步复现报错；随后补齐地形和短队列撤权的失效处理，复测通过。[回归脚本、失败样本和最终日志](qa.zip)
- 最终资源包在 Godot 4.7.2 Standard 上通过导入与真实 DLL 调用自检。MOV 脚本 SHA-256 为 `056c7920e8450c40fccee5ade6e216ad40ef8f9c9a3264775f0c4f09976d963c`，DLL 为 `ed315ce1df4bbb573ecf7d8e77a7e24dd0cb80c136611ce5aa72f053d4a00730`。隔离包包含生成的 `field_movement.gd`、`field_pipeline.gd`、适配器源码、C++ 源码、扩展配置和编译命令。[试玩文件及源码](experiment.zip)

本轮每种配置每个输入场景测一场，未测千人战场、多人联机和其它硬件。P2 的完整阶段门禁待验收。
